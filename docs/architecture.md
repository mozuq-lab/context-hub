# 構成とデータ

ContextHubはCapture、Organize、Writer、Retrieveを分けます。coreはOpenClawから独立し、CLIとMockLlmで中核を検証できます。

| 部分 | 役割 |
|---|---|
| Capture | InputのREQやDiscordの入力を受け、原文・日時・出典・IDを保存 |
| Organize | 原文と既存プロジェクト定義をモデルへ渡し、分類・要約・関連候補のJSONを取得 |
| Writer | スキーマ、パス、ロック、ハッシュを検証し、許可された生成物と処理記録を更新 |
| Retrieve | 検索、プロジェクト再開、文字数制限付きのコンテキスト出力 |

## Vault

```text
Input/                         端末が追加する不変の受付ファイル
00_inbox/                      正式原文・訂正原文
10_projects/<id>/project.md     プロジェクト定義
10_projects/<id>/NOW.md         現在地・次の一手・未解決の生成ビュー
10_projects/<id>/HISTORY.md     月ごとの経緯の生成ビュー
10_projects/<id>/REFERENCES.md  参考資料に分類されたメモとURLの生成ビュー（資料があるプロジェクトだけ）
20_ideas/                      AI整理済みアイデア
30_knowledge/                  共通へ採用した正式知識・方針
40_people/<id>/person.md        本人が登録した人の定義（名前・呼び名）
40_people/<id>/SUMMARY.md        その人が出てくる記録と未完了の項目の生成ビュー
40_people/PEOPLE.md            登録した人の一覧の生成ビュー（人を登録したときだけ）
10_projects/<id>/knowledge/     対象projectへ採用した正式知識・方針
POLICY.md                      共通の有効方針（派生集約）
10_projects/<id>/POLICY.md      対象projectの有効方針（派生集約）
90_system/                     受領・処理・訂正解釈・候補・承認・作成・状態変更・定義変更・統合・解決報告（誤りとして外す報告を含む）・読み直しの結果・期日・「片付いたかも」の見送り・下書き・競合とその片付けの記録
90_system/people/              人の登録・変更・外した記録
90_system/idea-links/          似ているアイデアを束ねる・別の話とする本人の判断
90_system/idea-index.json      似ているアイデアの候補と束（派生。アプリが読む）
90_system/unassigned-actions.json プロジェクト未定のメモのタスク候補とAIの提案（派生。アプリが読む）
90_system/synthesis/           週次の統合の実行の記録（設定で有効にしたときだけ）
90_system/insights.json        今週の気づき（派生。アプリが読む。設定で有効にしたときだけ）
90_system/insight-reactions/   今週の気づきへの本人の反応（役に立った・的外れ）
90_system/privacy/patterns.json 設定の伏せ字の追加規則（派生。アプリが読む）
90_system/item-occurrences/    定例の回の完了・見送りの記録
90_system/answers/             記録に聞くの問いと答え（30日で片付ける）
90_system/client-preferences.json アプリの好み（ピン留め・ひな形・文脈かごの上限）を端末間でそろえる共有の記録
HOME.md                        受領と整理状況への入口
REVIEW.md                      直近の期間のふりかえり（派生）
_ContextHub/                   共有する入力ツールとテンプレート
.claude/skills/                Claude Code用のスキル（選んで深掘り、任意）
```

ロック、ログ、個人設定、認証情報、バックアップはVaultの外へ置きます。バックアップから復元できるかを確かめた結果だけは、`90_system/backup-checks/`に記録します（アーカイブのファイル名と件数だけで、保存先のパスや本文は含みません）。端末別のObsidian設定は標準では同期しません。

## 原文と生成物

原文は作成後に変更しません。同じイベントの再送は重複保存を防ぎ、別イベントの同じ文章は別の入力として保持します。REQは端末保存の記録、正式なIN IDはMiniでの原文保存の記録です。

昨日の会議を今日書くように、本人が後から記録するメモ・作業要約には**出来事の日付**（`happened_on`、`YYYY-MM-DD`）を付けられます（アプリの対応版、`ctx add --happened-on`、`submit-input.mjs --happened-on`、受付ファイルの`happened_on`）。付けた原文は、発生日時（`occurred_at`）をその日の正午（設定の`timezone`）にし、実際に書いた日時を`recorded_at`に残します。経緯・最終根拠・停滞の判定・NOWの最新の作業要約・検索の並びは発生日時を使うため、出来事の日付の順になります（後から書いた古い作業要約が、新しい作業要約の現在地を押しのけません）。NOW・検索・contextでは「2026-11-18のこと（記録 2026-11-20 09:00）」のように両方を示し、整理のモデルには本文の「明日」「来週」などをその日を基準に読むよう伝えます。記録した日より後の日付と、設定の`capture.maxBackdateDays`（既定365日）より前の日付は理由付きで受け付けません。記録した日と同じ日付は、指定がないのと同じに扱います。訂正は元のメモの出来事の日付を引き継ぎます。ふりかえり（REVIEW.md）の期間は受領日時で区切るため、後から書いたメモも届いた週のふりかえりに入ります。

HOMEを作るたびに`90_system/intake-features.json`へ、受け付ける依頼の種類（`operations`）、メモに付けられる項目（`capture_fields`）、出来事の日付をさかのぼれる日数（`max_backdate_days`）、期日のカレンダーの件名の設定（`calendar_titles`）、期日の依頼に添えられる欄（`item_schedule_fields`。`repeat`は定例）、「記録に聞く」が有効かと問いの上限の文字数（`ask`）を書きます。端末はこれを読んで、古い本体が受け付けない依頼を出さず、本体の設定に合わせます。

モデルは保存先やIDを決めません。結果はスキーマで検証し、出典・日時・未検証表示を維持します。分類不能のunclassifiedは正常な結果であり、処理成功と内容の確認済みは別です。

訂正のない100文字以下のメモは、モデルの言い換えを使わず、本人の言葉（空白と改行をまとめた1行。[秘密情報らしい文字列](operations.md#秘密情報らしい文字列を伏せる)は伏せ字）を要約として記録します。短いメモを言い換えても情報は増えず、本人の言葉が失われるためです。アイデアのファイル・一覧・検索にも本人の言葉が出ます。100文字を超えるメモ、作業要約、訂正のあるメモは、モデルの要約を使います。短いメモ1件を言い直しただけの知識の候補（`knowledge`）は作りません。本人が明言した判断・好みの候補（`decision`・`preference`）は短いメモからも作ります。整理の依頼でも、要約は原文の言葉を保つこと、知識の候補は本人が判断・方針・好みを明言した場合か再利用できる具体的な事実がある場合に限ることを伝えます。すでに整理済みのメモの処理記録は書き換えません。

NOWは根拠から決定的に組み立てます。古い入力で新しい状態を巻き戻さず、AI自己報告、提案、未確認、訂正未反映を分けます。自動領域の手動変更は無断上書きせず競合へ退避し、手動領域は保持します。

## 訂正と承認

訂正は元原文を残した新しい入力です。最新の訂正チェーンと整理済みの解釈を区別し、未反映なら旧要約を最新の確定事項として扱いません。

プロジェクトや恒久知識を確定する操作には、人が確認した候補とハッシュ等を結び付けます。モデルの本文に「承認済み」とあっても承認になりません。同期Vaultへ任意書き込みできるローカルプログラムを隔離する本人認証の仕組みではありません。

## 実行と同期

端末はInputへ新規ファイルを追加し、Miniが正式原文と生成物を書きます。Mini内のWriterは共通ロックで排他しますが、このロックは他端末やSyncthingの変更を排他しません。整理は別の整理用ロックで実行全体を排他し、Writerロックは対象の選択と結果の確定の短い区間だけ取得します。モデルの応答を待つ間もメモの保存・受付・承認は進みます。待機中に訂正が届いた入力、プロジェクト定義や有効方針が変わった入力は書き込まず、次回の整理で処理します。待機中に原文が書き換えられた場合は整合性違反として停止します。共有端末とローカルプロセスを信頼し、正式原文や処理記録の直接編集を避ける運用が前提です。

Writerロックの1区間では、原文（`00_inbox`）・訂正履歴・処理記録・項目の解決記録をそれぞれ1回だけ読み、同じ区間で候補や承認ごとに読み直しません。区間内でVault経由の書き込みがあれば、その場所の読み取りは捨てて読み直します。区間をまたいで使い回さないため、モデルの応答を待つ間の原文の書き換えは、これまでどおり確定時の再検査で検出します。メモの保存（`capture`）の再送判定は、先にイベント記録を見てその原文1件だけを読みます。イベント記録のない原文がある（原文とイベント記録の件数が違う）ときだけ全原文を調べ、再送でイベント記録を回復します。

受付（`ingest`）は、受領記録（`90_system/intake/REQ-*.json`）が今の受付ファイルの内容と一致する依頼をWriterロックを取らずに飛ばします。受領記録は作るだけで消さないためです。停止回復記録（`90_system/intake/pending/`）は受領記録と同じロック内で片付け、以前の版が残した記録も受領記録と一致すれば片付けます。古い訂正対象など理由付きで拒否した依頼は、同じ内容のままなら再実行せず、受付エラーの記録（`90_system/intake-errors/`）も書き直しません。理由のない失敗だけを、古い試行から順に再試行します。Writerの混雑でロックを取れない回は、その依頼を保留にして次回に続けます。

モデルへ渡すプロンプトは、送る直前に秘密情報らしい文字列を伏せ字にします（[運用](operations.md#秘密情報らしい文字列を伏せる)）。原文は書き換えず、作業要約のラベルとの照合もモデルが見たのと同じ伏せ字の本文で行います。

プロンプトはUTF-8で120KiBを上限とし、超える入力はモデルを起動せず`prompt-too-large`の失敗として記録します。上限は本文・訂正履歴・有効方針の合計に適用されます。Linuxの引数長制限（1引数128KiB）に余裕を持たせた値です。

cycleのモデル不要受付とAI処理枠は別です。`cycle --limit 2`は整理・承認回復・再関連付けを合計2件まで処理します。形式不正時の再問い合わせがあるため、件数は厳密な料金上限ではありません。

[週次の統合](weekly-synthesis.md)は、設定で有効にしたときだけ、`cycle`が整理の後に間隔ごとに1回実行します。整理と同じ整理用ロックで1つずつ実行し、モデルを待つ間はWriterロックを持ちません。モデルを呼ぶ前に実行の開始を記録するので、途中で止められた実行を次の`cycle`で呼び直しません。渡すメモは件数の上限で区切り、応答の根拠はコードが入力IDへ対応付けて、渡していないメモを挙げた項目を落とします。結果はAI生成・未検証の表示のまま、HOME・ふりかえり・`90_system/insights.json`に出します。`--limit`の件数には数えません。本人がアプリで付けた反応は受付ファイル（`insight-reaction`）で、問いへの答えはmeta付きのメモで届き、次の統合に渡します。

[記録に聞く](ask.md)は、CLIでは呼んだその場で、アプリからの問いは受付で答え待ちとして記録し、`cycle`が整理の後に答えます。週次の統合と同じ整理用ロックで1つずつ実行し、モデルを待つ間はWriterロックを持ちません。

アプリの好み（ピン留めと並び順・メモのひな形・文脈かごの上限）は、アプリが`operation: client-preferences`の受付ファイル（本文が変えたまとまりのJSON）で送り、本体がまとまりごとに新しい方を`90_system/client-preferences.json`へ残します。遅れて届いた古い変更で巻き戻さず、端末の時計が進みすぎていても受け付けた時刻より新しい日時は記録しません。ひな形に秘密情報らしい文字列があれば、理由付きで断ります。本体は好みの中身を使いません。既読・ウインドウの位置・通知の許可・APIキーのような端末ごとの状態は扱いません。
