# 候補の確認待ちを使う

HOMEの「確認待ち」から、プロジェクト案・知識・判断や方針・好みを確認できます。自分で作った候補と、入力からAIが抽出した未承認候補を扱います。「要確認」は新しい訂正・破損・同期不足など、「判断履歴」は採用・却下と反映状態です。

ObsidianではQuickAddの `approveKnowledge` / `rejectKnowledge` を追加します。知識・判断・好みを共通で扱います。プロジェクト案は `approveProject` / `rejectProject` を使います。候補・理由・元のメモ・置き換え元を読み、確認して依頼を保存してください。取消や保留は保存しません。[QuickAddの設定手順](../examples/quickadd/README.md)に従ってください。

専用Flutterクライアントはホームまたはメニューの「確認待ち」から同じ候補を開けます。詳細の元メモを確認し、採用・却下を依頼します。保留は閉じるだけです。サンプルや開発用クライアントの検証結果を、実Vaultへの適用済みと読み替えないでください。

依頼は `Input/REQ-….md` に空本文の新規要求として保存します。正式データの作成はMiniが行います。端末保存→同期→Miniでの再検証→判断記録→反映の順で進みます。承認記録があるのに反映がまだなら「承認済み・反映待ち」と表示します。二重の同じ判断は同じ正式データへ集約し、反対の判断は先に確定したものを維持します。

元のメモに訂正がある場合は、候補本文が同じでも古い候補を採用できません。同期し、Miniの再整理と一覧更新を待ってください。既存REQや候補・承認記録を直接編集して再送しないでください。保存結果が不明な場合は、専用クライアントの受付状況で同じ操作を確認します。

本体の `dashboard` または `cycle` がHOMEと派生一覧 `90_system/review/index.json` を再生成します。大きい一覧は512KiB以下のpageに分け、rootが各pageのhashを参照します。正本はMarkdownの候補と承認JSONであり、このindexは再生成可能です。端末は各依存ファイルのhash・想定未作成・追加訂正を確認し、同期途中の候補からの操作を止めます。

公開・導入時は本体を先に公開し、そのcommitを固定するクライアントを公開します。実運用への適用は別途、本体コード、Obsidianスクリプト/Macro、Flutter APK、旧Electron読取互換版の差分を確認して行います。本体が一覧を生成していない状態では、新クライアントは確認待ち一覧の未同期を表示します。

## 同じ対象を指すプロジェクト案

似た内容のメモが続くと、同じ対象を指すプロジェクト案が別々にできます。確認待ちでは、これらを1件にまとめて示します。

- 名前か別名が一致する案と、4文字以上の名前がもう一方の名前に含まれる案を、同じ対象とみなします（大文字小文字・全角半角を区別しません）。別名は一致だけを見ます。「アプリ開発」のような広い別名がほかの案の名前に含まれても、まとめません。
- ほかの案と最も多く重なる案を代表にします（同数なら名前が短い案、次に古い案）。1組に入れるのは、代表と直接重なる案だけで、古い順に20件までです。代表とは重ならない案は、別の組か単独の案として並びます。
- HOMEとふりかえりは1組を1件と数え、代表の行に「根拠のメモN件」を添えます。HOMEには、まとめた案の名前も示します。
- 候補のファイルは書き換えません。一覧（`90_system/review/index.json`）の代表の行に`duplicates`、まとめられた案の行に`duplicateOf`を付けます。
- 専用クライアントの対応版は、代表を採用・却下するときに、まとめた案のIDとハッシュ（`cover_ids`・`cover_hashes`）を添えて依頼します。Miniは、添えられた案のそれぞれが今も確認待ちで、判断する案と同じ対象を指し、内容が変わっていないことを確かめてから、全部に同じ判断を記録します。1件でも合わなければ、依頼の全体を受け付けません。採用で作るプロジェクトは代表の1つだけです。
- まとめて判断された案は、判断履歴に「（「代表の名前」とまとめて判断）」と示します。一覧の行には`coveredBy`（代表の案のID）が付き、`decisionId`は代表の案の判断記録を指します。
- QuickAdd・CLI・対応前のクライアントは1件ずつ判断します。代表だけを却下すると、残りの案は確認待ちに残ります。代表だけを採用すると、名前か別名が代表と一致する案は、同じ名前のプロジェクトができたため要確認へ移り、それ以外の案は確認待ちに残ります。
- まとめた判断の後に届いた同じ判断は、同じ記録へまとめます。代表だけの採用・却下（QuickAdd・CLI・対応前のクライアントから）、まとめた案の一部だけを添えた依頼、まとめられた案への同じ判断が当たります。反対の判断と、記録にない案を添えた依頼は受け付けず、先に確定した判断を保ちます。
- 読めない判断記録がある間は、どの案がまとめて判断済みかを確かめられません。Miniはその間、プロジェクト案の採用・却下を受け付けません（記録を直すと、同じ依頼を受け付けます）。この状態では`organize`と`cycle`も止まるので、端末の一覧は直前のままです。`dashboard`で一覧を作り直すと、判断前のプロジェクト案を要確認として示します。`doctor`が読めない記録のパスを示します。

## 採用先

採用先は元メモの明示指定とAI推定を区別して確認します。共通は本人の明示選択です。採用履歴から適用停止も依頼できます。[採用後の扱いとAI接続](policies.md)を参照してください。
