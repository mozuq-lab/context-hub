# プロジェクトの状態・統合・ふりかえり・経緯・資料

数日〜1週間あいた後に「何が動き、何が止まっているか」を確認するための機能です。いずれもモデルを使わず、受領・整理の記録から決定的に生成します。要約や抽出はAI生成・未検証のまま表示します。

## プロジェクトの作成

プロジェクトは、Miniで`project add`を実行するか、AIのプロジェクト案を採用して作ります。[Mac・Androidアプリ](https://github.com/mozuq-lab/context-hub-flutter-client)の対応版からは、名前・別名・キーワードと任意の最初のメモを入れて作成を依頼できます。依頼は`operation: project-create`の受付ファイルで、次の`cycle`（または`ingest`）で反映します。

```yaml
operation: project-create
project_id: project-<ULID小文字26文字>
title: 家庭菜園
aliases: [菜園]
keywords: [栽培]
confirmed: true
```

- IDは依頼側がプロジェクト案の採用と同じ`project-<ULID>`形式で決めます。
- 名前・別名が既存のプロジェクトのID・名前・別名と重なる場合（大文字小文字・全角半角を区別しない）や、同じIDがある場合は作らず、HOMEの「失敗と競合」（断ってから7日間）とアプリの受付状況に理由を表示します。
- 本文は任意の最初のメモです。空でなければ、作ったプロジェクトの入力（`memo`）として同じ出典・日時で保存します。
- 作成は`90_system/project-creations/PCR-*.json`に記録し、定義の書き込み前に停止しても同じ受付IDで回復します。最初のメモも同じ受付の再送では重複保存しません。

プロジェクトが増えると再関連付けの対象が更新され、過去のメモも新しいプロジェクトの関連候補として見直されます（モデル呼び出しを伴います）。

## プロジェクトの状態

`project.md`の`status`は、本人が切り替える次の3つの状態を持ちます。

| status | 表示 | 扱い |
|---|---|---|
| `active` | 進行中 | HOMEの一覧に表示し、整理と再関連付けの帰属候補としてAIへ渡す |
| `paused` | 休止 | HOMEの「休止・完了」へまとめ、AIの帰属候補から外す |
| `done` | 完了 | 休止と同じ |

旧版で書いた`active`以外の自由記述は進行中として扱い、HOMEに元の値を併記します。休止・完了のプロジェクトでも、入力で人が明示した`--project`はそのまま帰属し、すでに付いている関連付けも保持します。休止・完了は、これから整理する入力へAIが提示する候補だけを変えます。AIが状態を変えることはなく、AIに状態変更の依頼ファイルを代作させないでください。

状態の変更は、確認した`project.md`のハッシュに結び付けて行います。ハッシュは`project list`で確認できます。

```sh
node packages/core/dist/cli.js --config "<設定ファイル>" project list
node packages/core/dist/cli.js --config "<設定ファイル>" project status <project-id> --set paused --hash <sha256> --confirm
```

[Mac・Androidアプリ](https://github.com/mozuq-lab/context-hub-flutter-client)の対応版からは`operation: project-status`の受付ファイルとして依頼し、次の`cycle`（または`ingest`）で反映します。0.3.0までのアプリは状態変更の依頼とREVIEW.mdの表示に対応していません。定義が確認後に変わっていた場合や、すでに同じ状態の場合は受け付けず、HOMEの「失敗と競合」（断ってから7日間）とアプリの受付状況に表示します。

変更は`project.md`のfrontmatterの`status`行だけを書き換え、ほかの行・コメント・改行は保持します。変更ごとに`90_system/project-status/PST-*.json`へ変更前後のハッシュを記録し、書き込み途中で停止しても、同じ受付ID（CLIでは同じ引数での再実行）で回復します。

状態を変えると`project.md`のハッシュが変わります。変更前のハッシュで確認していた採用先付き方針の候補は、再確認が必要になります。状態だけの変更では再関連付け（モデル呼び出し）は起きません。

## 名前・別名・キーワードの手入れ

AIがメモをどのプロジェクトに結び付けるかは、`project.md`の名前（`title`）・別名（`aliases`）・キーワード（`keywords`）に左右されます。作った後の定義は、状態と同じく確認したハッシュに結び付けて書き換えます。

```sh
node packages/core/dist/cli.js --config "<設定ファイル>" project list
node packages/core/dist/cli.js --config "<設定ファイル>" project edit <project-id> \
  --add-alias ベランダ菜園 --remove-keyword 栽培 --add-keyword 苗 --hash <sha256> --confirm
```

`--title`で名前を変え、`--add-alias`・`--remove-alias`・`--add-keyword`・`--remove-keyword`は何度でも指定できます。前後の空白を除き、大文字小文字や全角・半角だけが違う重複は最初の1つにまとめます。名前は1〜200文字、別名とキーワードはそれぞれ50件まで・1件100文字までです。定義にない語の削除や、変更のない指定は受け付けません。

[Mac・Androidアプリ](https://github.com/mozuq-lab/context-hub-flutter-client)の対応版からは`operation: project-definition`の受付ファイル（`project_id`・確認した`project_hash`・変更後の`title`・`aliases`・`keywords`の全体・`confirmed: true`、本文なし）として依頼し、次の`cycle`（または`ingest`）で反映します。定義が確認後に変わっていた場合は受け付けず、HOMEの「失敗と競合」（断ってから7日間）とアプリの受付状況に表示します。

書き換えるのは`title`・`aliases`・`keywords`だけで、ほかのキー・コメント・本文は保持します。変更ごとに`90_system/project-definitions/PDEF-*.json`へ変更前後の定義とハッシュを記録し、書き込み途中で停止しても、同じ受付ID（CLIでは同じ引数での再実行）で回復します。

定義が変わるとプロジェクト登録簿のハッシュが変わるため、帰属未確定のメモ（プロジェクトを指定せず、AIの確信度もしきい値未満だったもの）は、次の`cycle`で新しい定義に対する再関連付け（モデル呼び出し）の対象になります。件数は`cycle --limit`の枠に含まれます。新しい定義での関連付けが済むまで（または失敗している間）は、同じ根拠に対する前回の関連付けのうち今もあるプロジェクトの分で、NOW・経緯・検索に表示し続けます。無関係なプロジェクトに別名を足しただけで、関連付け済みのメモが一時的に消えることはありません。

### 定義が壊れたとき

Obsidianなどで`project.md`を手で書き換えて形式が崩れると、プロジェクトの一覧を組み立てられません。不正な定義を除いて続けると登録簿のハッシュが変わり、帰属未確定の全メモが再関連付けの対象になってしまうため、ContextHubは整理を止め、モデルを呼びません。そのかわりに、どのファイルのどの項目が不正かを次の場所に示します。

- `ctx doctor`: `プロジェクト定義が不正です: 10_projects/<id>/project.md（別名（aliases））`のように、ファイルと項目を1件ずつ表示します。
- HOME: `cycle`・`dashboard`は「プロジェクト定義の不正」だけのHOMEを書き、直すべきファイルと項目を一覧にします。
- `cycle`などのコマンドのエラー: 同じファイルと項目を示します。

端末からのメモは受け付けて記録し、失われません（プロジェクトへの関連付けは定義を直すまで待ちます）。定義の不正があるあいだは、ほかのプロジェクトの名前・別名・キーワードの変更も受け付けません。定義を直すと、次の`cycle`で通常のHOMEに戻り、整理を再開します。

## プロジェクトの統合

同じものを指すプロジェクトが2つできてしまったとき（AIのプロジェクト案を採用した後で既存のものと同じだと気付いた、呼び名が変わって作り直した、など）は、一方を他方へ統合できます。統合元は残したまま「統合済み」になり、統合元の入力・完了報告・日付は統合先のものとして読みます。

```sh
node packages/core/dist/cli.js --config "<設定ファイル>" project list
node packages/core/dist/cli.js --config "<設定ファイル>" project merge <統合元のid> --into <統合先のid> \
  --hash <統合元のsha256> --into-hash <統合先のsha256> --confirm
node packages/core/dist/cli.js --config "<設定ファイル>" project unmerge <統合元のid> \
  --hash <統合元のsha256> --into-hash <統合先のsha256> --confirm
```

統合は、確認した両方の`project.md`のハッシュに結び付けます。[Mac・Androidアプリ](https://github.com/mozuq-lab/context-hub-flutter-client)の対応版からは`operation: project-merge`（取り消しは`project-unmerge`）の受付ファイルとして依頼し、次の`cycle`（または`ingest`）で反映します。

```yaml
operation: project-merge
project_id: <統合元のid>
project_hash: <統合元のproject.mdのsha256>
into_id: <統合先のid>
into_hash: <統合先のproject.mdのsha256>
confirmed: true
```

統合で書き換えるのは、次の2つの定義だけです。

- 統合元の`project.md`: `status`を`done`にし、`merged_into: <統合先のid>`を加えます。名前・別名・キーワード・本文は保ちます。
- 統合先の`project.md`: 統合元の名前と別名を別名に、キーワードをキーワードに加えます（既にある語、100文字を超える語、50件の上限を超える分は加えません）。これで、古い呼び名で書いたメモも統合先に結び付きます。

原文、処理記録、完了・解決の報告、期日の記録は書き換えません。読むときに、統合元を指す帰属（本人の指定とAI推定の関連）を統合先へ読み替えます。

| 対象 | 統合後の扱い |
|---|---|
| 統合元の入力 | 統合先のNOW・経緯・資料・検索・ふりかえりに含める。本人が統合元を指定したメモは本人指定のまま扱う |
| 完了・解決の報告、期日と見直す日 | 統合先のNOWに同じ項目が並んでいれば、その項目に引き継ぐ |
| 「片付いたかも」とその見送り | 統合先のNOWに同じ項目が並んでいれば、その項目に引き継ぐ |
| 統合後に統合元を指定して届いたメモ | 受け付けて、統合先の入力として整理する |
| 統合元のプロジェクト限定の方針 | 移さない。HOMEの「統合済み」に件数を示すので、必要なものは統合先へ採用し直す |
| 統合元のNOW・経緯・資料 | NOWは根拠なしになり、経緯と資料には統合したことと統合先を示す |
| 統合元に結び付けた[コミット履歴からの作業記録の下書き](work-records.md#コミット履歴からの作業記録の下書き) | 作らない。`cycle`の結果に、設定のプロジェクトを統合先へ変えるよう示す |

NOWの「次の一手」は、統合後も最新の作業要約のものだけです（未解決は統合元の入力からも集めます）。統合元の作業要約のほうが古ければ、その次の一手はNOWに並ばず、付けていた日付はHOMEの「日付を付け直す項目」に出ます。

統合済みのプロジェクトはHOMEの「統合済み」に統合先と並べて示し、AIの帰属候補から外します。統合済みのプロジェクトへの状態・名前の変更、完了報告、期日の設定、方針の採用は受け付けず、統合先を示します（受付では理由`project-merged`）。読むだけの操作（`resume`・`find --project`・`bundle`・`policies --project`、OpenClawプラグインのプロジェクト限定方針）は、統合済みのプロジェクトを指定すると統合先として扱います。

次の統合は受け付けません。先に取り消すか、統合先を選び直してください。

- すでに統合済みのプロジェクトを統合元にする、統合済みのプロジェクトを統合先にする
- ほかのプロジェクトの統合先になっているプロジェクトを統合元にする
- 確認後にどちらかの定義が変わっている（理由`project-merge-changed`）

取り消すと、統合元は統合前の状態（進行中・休止・完了）に戻り、帰属・完了報告・日付の読み替えも止まります。統合で統合先に加えた語は、取り消しの時点で残っていて、同じ統合先に統合されたままのほかのプロジェクトが持たないものだけを外します。統合の後に統合先を指定して届いた入力は統合先に残り、統合元を指定して届いた入力は統合元に戻ります。統合している間に統合先で付けた完了・解決の報告・誤りとして外した記録・日付・「片付いたかも」の見送りは記録を書き換えず、本人が統合元を指定した入力から出た項目のものだけ、統合元の項目として読みます。統合の前や取り消しの後に統合先で付けた記録は、統合先のままです（記録の日時と統合・取り消しの記録の日時で判断します）。取り消しで外す語は、取り消し済みの統合で足して、その取り消しで外した語を含みません（その後に手で足した同じ語は残します）。

統合と取り消しは`90_system/project-merges/PMG-*.json`へ変更前後のハッシュと加えた語を記録し、書き込み途中で停止しても、同じ受付ID（CLIでは同じ引数での再実行）で回復します。定義が変わるとプロジェクト登録簿のハッシュが変わるため、帰属未確定のメモは次の`cycle`で再関連付け（モデル呼び出し）の対象になります。

`merged_into`を手で書いた場合も同じように読み替えます。統合先が見つからない、統合先が循環している場合は統合として扱わず（操作も帰属候補も止めません）、HOMEの「失敗と競合」と`doctor`に示します。統合先がさらに統合されている場合は、最後の統合先として読み替えたうえで同じ場所に示します。

## 停滞の表示

HOMEの一覧には各プロジェクトの最終根拠（NOWの`last_evidence_at`）と経過日数を表示します。進行中で、最終根拠から`retrieve.staleDays`（既定14日）を超えたプロジェクトは「停滞しているプロジェクト」に分けて、長く止まっている順に並べます。再開するか、休止・完了にするかを判断する目安です。NOWが未生成のプロジェクトは停滞に含めません。

## ふりかえり（REVIEW.md）

`cycle`はHOMEの前にVault直下の`REVIEW.md`を生成し、HOMEからリンクします。単独では`digest`で生成できます。

```sh
node packages/core/dist/cli.js --config "<設定ファイル>" digest
node packages/core/dist/cli.js --config "<設定ファイル>" digest --days 30
```

既定の期間は直近`retrieve.digestDays`日（既定7日）です。次の内容を含みます。[週次の統合](weekly-synthesis.md)を有効にしている場合は、「概要」の前に「今週の気づき」を出します。

- 期間内に届いた入力の件数（整理済み・整理待ち・整理失敗）と、プロジェクト未帰属の件数
- 動きのあったプロジェクトごとの新しい入力、主な入力の要約、「現在地」「次の一手」の変化
- 期間より前から残っている未解決（解決済みかは判定しません）
- 動きのなかった進行中のプロジェクトと、休止・完了のプロジェクト
- 確認待ちの候補と、候補が作られてからの日数

「現在地」「次の一手」の変化は、NOWと同じく最新の作業要約の確認済み項目を、期間開始の時点で有効だった解釈（開始までに届いた原文・訂正のうち最後に整理されたもの）と比べたものです。期間は受領日時で区切り、期間内に届いた訂正も入力として数えます。経過日数は24時間単位です。HOMEと同じく生成物として扱い、手で編集された`REVIEW.md`は上書きせず`90_system/conflicts/`へ退避します。

## 経緯（HISTORY.md）

`cycle`はプロジェクトごとに`10_projects/<project-id>/HISTORY.md`を生成します。NOWは「今」、ふりかえりは直近の期間だけを示すため、休止から戻るときや完了にするときに、そのプロジェクトがどう進んできたかを通して読むためのものです。単独では`history`で作り直せます。

```sh
node packages/core/dist/cli.js --config "<設定ファイル>" history
node packages/core/dist/cli.js --config "<設定ファイル>" history <project-id>
```

モデルは使わず、根拠と処理記録から月ごとに次の出来事を並べます。

- 届いた入力の件数と、入力ごとの日付・種類・要約（1か月に8件まで。残りは件数だけ）
- 現在地の移り変わり（作業要約を発生日時の順に並べ、直前の作業要約と確認済みの現在地が変わったときの追加・外れた項目）
- 完了・解決の報告と、未解決への戻し
- 状態の切り替え、プロジェクトの作成と名前・別名・キーワードの変更
- このプロジェクトに採用した知識・方針と、その適用停止

休止・完了のプロジェクトでは、末尾の「いま残っているもの」に最後の現在地と、残っている次の一手・未解決をまとめます。現在地と次の一手はNOWと同じく根拠に照合できたものだけを使います。日付は設定の`timezone`で表示し、「何日前」のような生成時点に依存する表現は使いません。本文が前回と同じなら書き込まないので、同期の差分は記録が増えたときだけ生じます。要約と抽出はAI生成・未検証です。

経緯は根拠から作り直せる派生物です。手で編集された`HISTORY.md`は上書きも退避もせずに更新を止め、HOMEの「失敗と競合」に「経緯の更新が止まっています」と示します。ファイルを消すと次の`cycle`で作り直します。状態の切り替えや解決報告などの記録に読めないものがあっても生成は止めず、その種類の出来事を省いたことを本文に示し、`doctor`でも示します。経緯の生成が失敗しても`cycle`のHOME生成は続けます。

## 資料（REFERENCES.md）

`cycle`は、参考資料（`reference`）に分類されたメモがあるプロジェクトに`10_projects/<project-id>/REFERENCES.md`を生成します。「あとで読む」「この仕様を見た」と書き留めたメモとURLを、プロジェクトごとに新しい順で見返すためのものです。単独では`references`で作り直せます。

```sh
node packages/core/dist/cli.js --config "<設定ファイル>" references
node packages/core/dist/cli.js --config "<設定ファイル>" references <project-id>
node packages/core/dist/cli.js --config "<設定ファイル>" find --project "<project-id>" --kind reference
```

モデルは使わず、整理済みの記録から月ごとに次の内容を並べます。

- 資料ごとの日付、AIの要約、原文へのリンク。訂正があれば「訂正あり」、AI推定で結び付いたメモには「関連候補（AI推定）」を付ける
- 本文から取り出した`http`・`https`のURL（1件のメモにつき10件まで）。同じURLは、それを載せた新しい資料にだけ載せる。URLは半角の文字が続く範囲とし、続けて書いた和文は含めない

URLの中身は取得しません。[秘密情報らしい文字列](operations.md#秘密情報らしい文字列を伏せる)を含むURLと500文字を超えるURLは載せず、件数だけ示します（原文で確認できます）。1つのプロジェクトに載せる資料は新しい順に200件までです。訂正で参考資料でなくなったメモは外れます。どのプロジェクトにも結び付いていない資料は、HOMEの「プロジェクト未定の資料」に示します。[統合済み](#プロジェクトの統合)のプロジェクトの資料は統合先の`REFERENCES.md`に並べ、統合元の`REFERENCES.md`には統合先への案内だけを残します。

経緯と同じく根拠から作り直せる派生物です。本文が前回と同じなら書き込まず、手で編集された`REFERENCES.md`は上書きも退避もせずに更新を止め、HOMEの「失敗と競合」と`doctor`に「資料の更新が止まっています」と示します。ファイルを消すと次の`cycle`で作り直します。資料のないプロジェクトにはファイルを作りません。生成が失敗しても`cycle`のHOME生成は続けます。要約と分類はAI生成・未検証です。
