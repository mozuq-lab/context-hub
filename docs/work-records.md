# NOW項目の完了・解決と、コミット履歴からの作業記録

NOWの「次の一手」「未解決」を本人の報告で片付ける・誤りとして外す機能と、開発リポジトリのコミット履歴から作業記録の下書きを作る機能です。どれも原文と整理結果（receipt）は書き換えず、本人の確認を経た操作だけを記録します。完了・解決の報告と下書きはモデルを使いません。誤りとして外した項目は、次の整理でモデルにメモを読み直させ、外した項目の本文・理由・一言をモデルへ渡します（下の「誤りとして外す」）。

## NOW項目の完了・解決

NOWの「次の一手」と「未解決」の各行は、作業要約で触れられない限り残り続けます。本人が「やった」「解決した」と報告すると、その行を該当欄から外して、NOW末尾の「解決済み・完了（本人報告）」へ移します。ふりかえり（REVIEW.md）でも、解決済みの項目を「期間より前からの未解決」から外し、期間内に報告した件数を表示します。

項目は「プロジェクト・欄・根拠の入力ID・本文」で識別します。複数のプロジェクトに関連付いた入力の項目は、プロジェクトごとに別の項目として報告します。同じ本文でも、新しい作業要約で再び報告された場合は別の項目として再表示します。報告は根拠の入力に結び付き、後から届いた報告を打ち消さないためです。

NOWを生成するたびに、項目とキーの一覧を`90_system/now-items/<project>.json`へ書きます。旧版で生成したNOWは、次の`cycle`で一覧を作り直します。報告はこの一覧にある項目だけを受け付けます。CLIでは次のように操作します。

```sh
node packages/core/dist/cli.js --config "<設定ファイル>" item list <project-id>
node packages/core/dist/cli.js --config "<設定ファイル>" item resolve <project-id> <key> --confirm
node packages/core/dist/cli.js --config "<設定ファイル>" item reopen <project-id> <key> --confirm
```

[Mac・Androidアプリ](https://github.com/mozuq-lab/context-hub-flutter-client)の対応版では、NOWの項目から`operation: item-resolution`の受付ファイルとして依頼し、次の`cycle`（または`ingest`）で反映します。報告ごとに`90_system/item-resolutions/RES-*.json`を残し、項目ごとに最後の記録（解決または再開）を有効とします。記録の作成後、NOWの再生成前に停止しても、同じ受付IDで再送すると再生成だけを行います。

受付は受付ファイルの名前順で、端末で操作した順ではありません。先に処理した依頼で項目が片付いていたり、NOWから消えていたり（同じメモの別の項目を「別のプロジェクトの話」として外すと、メモごとプロジェクトから外れます）すると、後の依頼は項目の状態を理由に拒否します（`item-missing`・`item-closed`・`item-open`）。同じ内容のまま送り直しても結果は変わらないため再試行せず、HOMEの「失敗と競合」（断ってから7日間）とアプリに何が起きた可能性があるかを示します。NOWを再読込して、必要なら新しく依頼してください。期日・見直す日の依頼（`item-schedule`）も、NOWにない項目は同じく`item-missing`で拒否します。

AIは完了・解決を判断しません（下の「片付いたかも」は候補を示すだけです）。AIに解決報告の受付ファイルを代作させないでください。

### 誤りとして外す（AIの読み違いの報告）

AIの要約が読み違えた項目、別のプロジェクトの話が紛れた項目、もう古い項目は、完了・解決とは別に「誤りとして外す」と報告できます。完了・解決に数えたくないものを、片付いたことにせずに外すための操作です。

```sh
node packages/core/dist/cli.js --config "<設定ファイル>" item exclude <project-id> <key> --reason misread --note "検討しただけで、まだ決めていない" --confirm
node packages/core/dist/cli.js --config "<設定ファイル>" item reopen <project-id> <key> --confirm
```

理由は次の3つから選びます。一言（`--note`）は任意で、200文字以内・1行です。

| 理由 | 意味 | 外したあとに起きること |
| --- | --- | --- |
| `misread`（読み違い） | メモはそう言っていない | 次の`cycle`で、そのメモを理由と一言を添えて読み直します |
| `wrong-project`（別のプロジェクトの話） | このプロジェクトの話ではない | AIが推定した関連付けなら、そのメモをこのプロジェクトから外し、読み直して関連先を見直します。本人がプロジェクトを明示して保存したメモは、関連付けを変えず、この項目だけを外します |
| `outdated`（もう古い） | 読みは合っているが、今は当てはまらない | 項目を外すだけで、読み直しません |

- 外した項目は、NOW末尾の「誤りとして外した項目（本人報告）」へ理由と一言を添えて移します。HOMEの「次の一手」と、ふりかえりの「期間より前からの未解決」からも外れます。プロジェクトの再開（`resume`）と別AI向けのcontextには、NOWと同じく「誤りとして外した項目」の欄として理由付きで出ます。ふりかえりと経緯（HISTORY.md）では、完了・解決とは別に「誤りとして外した」と数えます。
- 読み直しは、整理（`organize`・`cycle`）の中で、新しいメモの整理と関連の見直しのあとに行います。1回の整理で扱う件数（設定の`organize.maxItemsPerRun`、または`--limit`）の残りの範囲で行い、残った分は次の整理へ回します。モデルの呼び出しはWriterロックの外で行い、反映の直前に、メモと訂正、報告が変わっていないことを確かめます。変わっていた場合は反映しません。
- 読み直した結果は`90_system/item-rereads/<入力ID>.json`に、receiptとは別の記録として保存します。receipt、原文、アイデアのファイル、承認待ちの候補は書き換えません。NOW・HOME・検索・contextは、この記録を重ねて表示します。読み直しに失敗したメモはHOMEの「失敗と競合」に示し、`organize --retry-failed`で`organize.maxAttempts`回まで再試行します。
- 外した項目の本文・理由・一言は、同じメモを読み直すときと、同じプロジェクトの次からの整理で、`excluded_items`として引用データとしてモデルへ渡します（同じメモの分と、ほかのメモの分をそれぞれ新しい順に10件まで。「もう古い」はほかのメモへは渡しません。秘密情報らしい文字列は、ほかの資料と同じく伏せ字にします）。同じ読み違いを繰り返しにくくするための材料で、モデルが項目を消す権限を持つわけではありません。
- `item reopen`で未解決へ戻すと、項目は元の欄へ戻り、読み直した結果と関連付けの変更も重ねなくなります。理由を変えるときは、いったん戻してから外し直します。
- 読み直しで本文が変わった項目、読み直した項目をさらに外して次の読み直しを待っている項目、メモごとプロジェクトから外れた項目も、「誤りとして外した項目」に残り、`item reopen`で戻せます。読み直した項目をさらに外した場合、次の読み直しが済むまでは今の読み直しを表示に使います。新しい作業要約に置き換わった次の一手は、完了・解決の報告と同じく一覧から外れます。
- 外したあとにメモを訂正した場合は、読み直した結果を重ねず、訂正後の整理結果を使います。「別のプロジェクトの話」として外したプロジェクトは、訂正後も関連から外したままです（receiptにはモデルの関連候補をそのまま記録し、読むときに除きます。未解決へ戻すと関連も戻ります）。訂正で本文が変わって元の項目がなくなった場合、外した記録は「いまの整理結果にはない項目」として一覧に残ります。不要なら未解決へ戻してください。
- 「別のプロジェクトの話」として外している間は、プロジェクトの定義が変わっても、そのメモの再関連付けをしません（外した状態で求めた関連を残すと、未解決へ戻しても元に戻らないためです。その間の関連の見直しは読み直しで行います）
- 統合済みのプロジェクトでは、外す記録もメモの関連も統合先のものとして読みます。本人が統合元を指定して保存したメモは、統合先でも本人の指定として扱い、「別のプロジェクトの話」でも項目だけを外します。AIが統合元へ推定したメモは、統合先から外れます

アプリからは、`operation: item-resolution`の受付ファイルに`action: exclude`、`reason`、任意の`note`を付けて依頼します。完了・解決と同じく、AIは誤りかどうかを判断しません。AIに受付ファイルを代作させないでください。

読み直しでも、承認待ちの知識・方針の候補とプロジェクト案は作り直しません。候補が読み違いに基づいている場合は、[候補の確認](candidate-review.md)で見送ってください。

### 片付いたかも（AIが見つける完了・解決の候補）

完了・解決の報告は忘れがちです。後から書いたメモに「〜を直した」「〜に決めた」とあるのに、NOWに古い項目が残り続けないよう、整理のときにAIが片付いた可能性のある項目を探します。AIが見つけるのは候補だけで、完了・解決にするのは本人の報告だけです。

- 対象は、プロジェクトを明示して保存したメモ・作業要約（アプリやCLIでプロジェクトを選んだもの。AIエージェントが`--project`を付けて保存した作業要約も含みます）だけです。AIが推定しただけの帰属では探しません。
- 整理のとき、そのプロジェクトの片付いていない「次の一手」「未解決」を、引用データとしてモデルへ渡します。次の一手を先に、未解決は根拠が新しい順に、合わせて30件まで（1件200文字まで）です。そのメモより後の根拠で挙がった項目は渡しません。項目を足すとプロンプトが上限を超える場合は、項目なしで整理します。モデルは、メモが「済んだ」「解決した」「不要になった」と明確に述べている項目を、メモの原文の引用付きで最大5件返します。予定や推測だけでは返しません。
- コードは、渡した項目への参照であること、引用が最新の原文にそのまま含まれ、文字・数字を4文字以上含むことを確かめ、合わないものは捨てます（整理全体は失敗にしません）。結果は処理記録（`90_system/receipts/`）の`resolution_hints`に残ります。
- NOWの「片付いたかも（AI推定・本人の確認待ち）」と、項目一覧（`90_system/now-items/`）の各項目の`hints`に表示します。HOMEの「次の一手」では「（片付いたかも・要確認）」と印を付けます。項目は元の欄に残したままです。
- 次の場合は示しません: 項目が完了・解決済みのとき、根拠のメモに未反映の訂正があるとき、本人が「違う」と見送ったとき、本人が「未解決に戻す」をした時点より前の整理から出た候補。

確定はこれまでどおり`item resolve`（アプリでは完了・解決の報告）です。違う場合は、そのメモからの候補だけを見送ります。見送りは`90_system/hint-dismissals/HDM-*.json`に残り、同じメモから同じ項目へは、そのメモを訂正した後も再び示しません。依頼の後に項目が完了・解決された場合など、候補が既に消えていても見送りは受け付けます。別のメモがその項目に触れたときは改めて示します。アプリの対応版は`operation: item-hint-dismiss`（`project_id`・`item_key`・`input_id`）の受付ファイルで依頼します。

```sh
node packages/core/dist/cli.js --config "<設定ファイル>" item list <project-id>   # maybe_done に候補と引用
node packages/core/dist/cli.js --config "<設定ファイル>" item resolve <project-id> <key> --confirm
node packages/core/dist/cli.js --config "<設定ファイル>" item dismiss-hint <project-id> <key> <IN-ID> --confirm
```

### 本人が追加する次の一手（行動）

NOWの「次の一手」に載るのは、ふだんは最新の作業要約から読み取った項目です。本人が「これをやる」と決めた行動は、AIの読み取りを介さずに直接載せられます。

- 行動は入力の種類`action`として、メモと同じく`00_inbox/`へ原文のまま保存します（出典・日時・入力ID付き。作成後は変えません）。本文は1行・200文字以内で、本人の言葉のまま示します。プロジェクトを指定すると、そのプロジェクトのNOWに載ります。統合済みのプロジェクトには追加できず、統合先へ追加します。プロジェクトを指定しない行動は、[プロジェクト未定の次の一手](#プロジェクト未定の次の一手)に載ります。
- モデルでは整理しません（処理記録も作りません）。保存した時点で、そのプロジェクトのNOWの「次の一手」に「本人が追加: 」を付けて、作業要約の次の一手より前に載せ、項目一覧（`90_system/now-items/`）にキー付きで書きます。項目一覧では`action`を持ちます。
- 新しい作業要約が届いても外れません。外れるのは、本人が完了、または誤りとして外すと報告したときだけです。完了・未解決へ戻す・期日と見直す日・「片付いたかも」は、ほかの項目と同じ操作で使えます。誤りとして外す理由は「もう古い」（`outdated`）だけです。行動はAIの読み取りではないため、読み違い・別のプロジェクトの話としては外せません（その理由で外した項目は、同じ読み違いを減らす例としてモデルへ渡すため）。
- AIが読み取った行（NOWの「提案」の欄の分類候補task・AI提案・提案と、作業要約の次の一手）を、本人が行動にすることもできます。文面は保存前に直せます。元の行はmetaの`action_from_input`（根拠の入力ID）・`action_from_text`（直す前の本文）・キー付きの項目なら`action_from_key`で指し、項目一覧の`action.from`に残します。行動にした行は、元の欄に二重に並べません（どのプロジェクトのNOWでも外します）。行動を完了・誤りとして外した後も、元の行は戻しません（本人が引き取った行のため）。行動にできるのは「提案」の欄の行と次の一手の項目で、未解決の項目は行動にできません。
- 文面を直すときは、元の入力への訂正（`correct`）を使います。元の文面は元の入力に残り、NOWは直した文面になります。直した行動は別の項目キーになりますが、付けていた期日・見直す日・繰り返しは引き継ぎます。AIの行を行動にしたときは、元の行に付けていた日付も引き継ぎます。行動には、直す前の文面・元の行に付けた記録を含めて最新の日付が効くため、文面を前の形へ戻しても、前の回の期日には戻りません。完了・誤りとして外した報告は引き継がないため、完了した行動を直すと未完了として戻ります。ファイルから渡した文面の末尾の改行1つは含めません。
- HOMEの「次の一手」、人ごとの見返し（未完了の項目として。名前が出てくる記録には数えません）、ふりかえり（期間内に追加した件数と、そのうち完了した件数）、経緯、検索（種類`action`）、`resume`・`context`に反映します。整理待ちには数えません。週次の統合には渡しません。

```sh
node packages/core/dist/cli.js --config "<設定ファイル>" item add <project-id> "見積もりを依頼する" --event-id <任意のID> --confirm   # --event-idを付けると、途中で止まった追加を同じIDで再送しても重複しない
node packages/core/dist/cli.js --config "<設定ファイル>" item add <project-id> --from-key <key> --confirm            # 作業要約の次の一手を行動にする
node packages/core/dist/cli.js --config "<設定ファイル>" item add <project-id> "直した文面" --from <IN-ID> --from-text "AI提案の本文" --confirm
node packages/core/dist/cli.js --config "<設定ファイル>" item add _unassigned "牛乳を買う" --confirm                    # プロジェクトを決めずに追加する
```

アプリの対応版は、`operation: capture`・`kind: action`・`project`（プロジェクト未定の行動では省く）と、行動にした行があれば上のmetaを付けた受付ファイルで依頼します。AIエージェントには行動の追加を代作させず、作業要約の「次の一手」に書かせてください。本人がそれを行動にします。

### HOMEの「次の一手」

HOMEの「次の一手（進行中のプロジェクト）」には、進行中のプロジェクトの次の一手のうち、まだ完了と報告していないものを、最終根拠が新しいプロジェクトから順に載せます。項目一覧（`90_system/now-items/`）から読み、1プロジェクトにつき3件までにして、残りは件数だけ示します。停滞しているプロジェクトも載せ、「（停滞）」と示します。休止・完了のプロジェクトと、NOWが未生成のプロジェクトは載せません。1件の本文は120文字までに切り詰めます。旧版で生成したNOWで項目一覧がまだない場合や、項目一覧が壊れている場合は「NOW項目の記録を読めないプロジェクト」として名前を示し、壊れているときは「失敗と競合」にも表示します。項目一覧は次の`cycle`で作り直されます。CLIの`item resolve`／`item reopen`もHOMEを作り直します。アプリの対応版では、同じ一覧を全件、未解決とあわせて「次の一手」画面で確認できます。

### プロジェクト未定の次の一手

どのプロジェクトにも結び付いていないメモは、どのNOWにも載りません。そのメモをAIが「タスク」と分類したことと、AIが挙げた次の一手の提案を、HOMEの「プロジェクト未定の次の一手」に新しい順で載せます。HOMEに載せるのはメモ5件、提案はメモ1件につき3件までです。訂正のない100文字以下のメモは本人の言葉、それ以外は「AI要約:」を付けたAIの一行要約で示し、原文へのリンクを添えます。

本人がプロジェクトを指定せずに追加した[行動](#本人が追加する次の一手行動)（「牛乳を買う」のような単発の行動）も、この一覧の先頭に「本人が追加: 」を付けて、追加した順に載せます（HOMEには10件まで）。

- 保存した時点で載ります（モデルでは整理しません）。メモの件数の上限には数えず、本人が完了・却下（「もう古い」）と報告するまで残ります。完了・未解決へ戻す・「今日の3つ」は、ほかの行と同じ操作で使えます。
- プロジェクトの項目と同じく、[期日・見直す日](#期日と次に見直す日)・[定例の繰り返し](#定例繰り返す期日)・[手間の目安](#手間の目安)を付けられます。期日が過ぎた・今日・7日以内の行動は、HOMEの「次の一手」の期日の欄にプロジェクトの項目と一緒に載せ（「プロジェクト未定 次の一手: 本人が追加: …」）、この一覧では件数だけを示します。期日がまだ先の行動と見直す日まで休ませている行動は、この一覧に「（期日 2026-12-01）」「（見直す日 2026-12-01）」のように付けて載せます（休ませている行動は期日の欄では件数だけに数えます）。文面を直しても、日付と手間の目安は同じ行動に残ります。CLIでは`item schedule _unassigned <key> --due 2026-12-01 --confirm`・`item effort _unassigned <key> --set quick --confirm`・`item done-round _unassigned <key> --confirm`のように使います。
- 行動はAIが読まないため、後からプロジェクトに結び付くことはありません。プロジェクトへ移す操作もありません（プロジェクトで追加し直し、元の行動を完了・却下します）。文面は訂正（`correct`）で直せます。直した行動は別の項目キーになり、完了・却下の報告は引き継ぎません。
- この一覧のAIの行（タスク候補・AI提案）を行動にすることもできます（プロジェクトを指定しても、しなくてもよい）。行動にした行は、プロジェクトのNOWと同じく一覧から外し、項目一覧にも残しません。プロジェクトのNOWの行を、プロジェクトを決めない行動にすることもできます（CLIでは`item add _unassigned --from <IN-ID> --from-text "元の本文"`。`--from-key`はプロジェクト未定の一覧の項目だけを探します）。元の行に効いていた期日・見直す日・繰り返し・手間の目安は、行動にした時点で行動の記録として写します（プロジェクトの行を別のプロジェクトの行動にした場合も同じ。写した記録の受付IDは`take-over:<行動の入力ID>:<元の記録のID>`）。写した元の記録は外した記録と同じに扱い、同じ本文の行が後から出直しても日付を付けず、付け直しも求めません。
- [ふりかえり](project-lifecycle.md#ふりかえりreviewmd)には「プロジェクト未定の行動」として、残っている件数と、期間内に追加・完了・却下した件数、最近完了した行動と古い順の残りを5件ずつ載せます。人ごとの見返し・経緯（プロジェクトごとの記録）には載りません。
- 項目一覧（`_unassigned.json`）では`action`を持ち、片付けた行動も（AIの行の上限とは別に）全件残します。`unassigned-actions.json`（メモの一覧）には載せません。本体が対応しているかは`intake-features.json`の`action_scopes`で、日付と手間の目安を受け付けるかは`item_record_scopes`で示します。

- 対象は、本人がプロジェクトを指定しておらず、AIの帰属の確信度も基準（`organize.projectThreshold`）未満の、整理済みのメモです。訂正の反映を待つメモは、古い解釈を行動として示さないよう載せません。
- 分類と提案はAI生成・未検証です。
- 行（タスクと分類したメモと、AIの提案の1件ずつ）には項目キーがあり、本人が完了にする、却下する（誤りとして外す・理由は「もう古い」だけ）、未解決へ戻すことができます。片付けた行はこの一覧から外れ、メモの行も提案もなくなったメモは一覧から消えます。メモの読み直しはしません。AIの行には期日・見直す日・手間の目安を付けられません（先に行動にします）。行のキーは表示する本文（伏せ字にした後・400文字まで）から作るため、伏せ字の規則を変えて本文の見え方が変わった行は、別の行として未解決に戻ります。
- 行の項目一覧は、プロジェクトの項目一覧と同じ形で`90_system/now-items/_unassigned.json`に書きます（`project`は`_unassigned`）。片付いていない行は、本人が追加した行動の全件と新しいメモ100件分、片付けたAIの行は新しい報告から30件までです（片付けた本人の行動は全件）。記録（`90_system/item-resolutions/`）の`project_id`も`_unassigned`になります。アプリの対応版は、行を「今日の3つ」に選び、完了・却下を`operation: item-resolution`・`project_id: _unassigned`の受付ファイルで依頼します。CLIでは`item list _unassigned`でキーを確かめ、`item resolve _unassigned <key>`のように使います。本体が対応しているかは`intake-features.json`の`item_scopes`で示します。
- プロジェクトを追加したり、名前・別名・キーワードを直したりして、メモがプロジェクトに結び付くと、この一覧から外れてそのプロジェクトのNOWに載ります。片付けた記録はプロジェクトへ引き継ぎません。
- 同じ内容を`90_system/unassigned-actions.json`（派生）に書き、アプリの対応版が「次の一手」とホームに表示します。新しい順に30件までを載せ、全体の件数を`total_memos`で、本文が本人の言葉かAIの要約かを`own_words`で示します。片付けた行は含めません（`task`を外し、提案から除きます）。内容が変わったときだけ書き直します。

### 期日と次に見直す日

「次の一手」「未解決」の項目には、本人が**期日**と**次に見直す日**を付けられます。どちらも任意で、`YYYY-MM-DD`の暦日を設定の`timezone`で解釈します。AIは日付を推測して付けません。

- 期日が過ぎた・今日・7日以内（今日〜6日後）の項目は、HOMEの「次の一手」の先頭に「期限切れ」「今日」「7日以内」として、プロジェクトをまたいで期日順に載せます。未解決の項目と、[プロジェクト未定](#プロジェクト未定の次の一手)の本人が追加した行動も含みます。
- 見直す日が先の項目は、その日まで「見直す日まで休ませている項目」として件数だけを示し、プロジェクトごとの一覧から外します。期日が7日以内に来る項目は、見直す日が先でも前に出します。
- 期日がまだ先の項目は、プロジェクトごとの一覧に「（期日 2026-12-01）」のように付けて載せます。NOWの行末にも「— 期日 …・見直す日 …」と示します。
- 新しい作業要約で次の一手の根拠が変わっても、同じ欄・同じ本文の項目が残っていれば日付を引き継ぎます。引き継いだ日付を外すと、引き継ぎ元の記録ごと外れます。
- 本文が変わるなどして引き継ぎ先がない日付は、HOMEの「日付を付け直す項目」に項目キーとあわせて示します。付け直すか、`item schedule <project-id> <key> --clear --confirm`で外してください（アプリには出ません）。解決済み・完了の項目には付けられず、その日付は付け直しにも出しません。

日付を使っていない間、HOMEの「次の一手」はこれまでと同じ形です。CLIでは次のように操作します。指定しなかった方は今の日付を保ち、`none`でその日付だけを外します。

```sh
node packages/core/dist/cli.js --config "<設定ファイル>" item schedule <project-id> <key> --due 2026-11-20 --confirm
node packages/core/dist/cli.js --config "<設定ファイル>" item schedule <project-id> <key> --review 2026-11-25 --confirm
node packages/core/dist/cli.js --config "<設定ファイル>" item schedule <project-id> <key> --due none --confirm
node packages/core/dist/cli.js --config "<設定ファイル>" item schedule <project-id> <key> --clear --confirm
```

アプリの対応版では`operation: item-schedule`の受付ファイル（`due`と`review_after`に変更後の全体、両方`null`で外す）として依頼します。プロジェクト未定の行動は`project_id: _unassigned`で依頼します（`item-occurrence`・`item-effort`も同じ。本体の対応は`intake-features.json`の`item_record_scopes`で示します）。指定ごとに`90_system/item-schedules/SCH-*.json`を残し、項目ごとに最後の記録を有効とします。項目一覧（`90_system/now-items/`）の各項目にも、そのときの日付を`schedule`として書きます。読めない記録はNOW・HOMEの生成を止めず、HOMEの「失敗と競合」と`doctor`で示します。

### 定例（繰り返す期日）

「毎週月曜にバックアップを確かめる」「月末に請求書を出す」のように繰り返す作業は、期日に**繰り返し**を付けて定例にできます。繰り返しは毎日・毎週・毎月と、N日・N週・Nか月ごと（Nは1〜12）から選び、期日のある項目にだけ付けられます。

- 定例の項目の**今回を完了**にすると、その回の完了を記録し、項目は欄に残したまま期日を次の回へ進めます。**今回だけ見送る**ときも同じく次の回へ進めます。次の回は、今の期日から間隔ずつ進めて今日より後になった最初の日です（遅れて片付けても過ぎた回をためず、早めに片付けたときは次の回へ進みます）。
- 毎月の繰り返しは、付けた期日の日を覚えます。31日のように短い月にない日は月末にし、次の月では元の日へ戻します（月末に丸めた期日のまま見直す日だけを変えても、覚えた日は変わりません）。
- 次の回には見直す日を引き継ぎません（見直す日はその回のためのものなので、必要なら次の回で付け直します）。次の回の期日が2099年を超えるときは進めず、理由を返します。
- 今回の完了・見送りは、本人が確認した回の期日を添えて依頼します。今の期日と違えば受け付けません（2台の端末から同じ回を片付けても、2回分は進めません）。
- 定例をやめるときは、繰り返しを外すか、ふつうの完了・解決の報告で項目を片付けます。
- NOWの行末とHOMEには「期日 2026-11-23（毎週）」のように示し、経緯（HISTORY.md）には各回の完了・見送りを載せます。

```sh
node packages/core/dist/cli.js --config "<設定ファイル>" item schedule <project-id> <key> --due 2026-11-23 --repeat weekly --confirm
node packages/core/dist/cli.js --config "<設定ファイル>" item schedule <project-id> <key> --repeat 2w --confirm     # 2週ごと（14d・3mなども使える）
node packages/core/dist/cli.js --config "<設定ファイル>" item done-round <project-id> <key> --confirm                # 今回を完了
node packages/core/dist/cli.js --config "<設定ファイル>" item skip-round <project-id> <key> --confirm                # 今回だけ見送る
node packages/core/dist/cli.js --config "<設定ファイル>" item schedule <project-id> <key> --repeat none --confirm   # 繰り返しを外す
```

アプリの対応版では、`operation: item-schedule`の受付ファイルに`repeat`（`{unit: day|week|month, every: 1〜12}`、`null`で外す）を添え、今回の完了・見送りは`operation: item-occurrence`（`action: done|skip`と、確認した回の`due`）で依頼します。`repeat`を省いた依頼（繰り返しを知らない版のアプリ）は、今の繰り返しを保ちます。回の記録は`90_system/item-occurrences/OCC-*.json`に残し、次の回の期日は新しい`SCH-*.json`として付けます。
### 手間の目安

「会議まで20分ある」「今日は半日まとまって使える」ときに合う項目を選べるよう、次の一手・未解決に本人が**手間の目安**を付けられます。目安は「15分ほど」（`quick`）・「1時間ほど」（`hour`）・「半日以上」（`half-day`）の3段階で、期日と同じくAIは推測せず、本人の指定だけを記録します。

- NOWの行末とHOMEの「次の一手」に「手間 15分ほど」のように示します（期日があれば「期日 2026-12-01・手間 半日以上」）。アプリの「次の一手」では目安で絞り込めます。
- 作業要約が届いて根拠が変わっても、同じ欄・同じ本文の項目には目安を引き継ぎます（期日と同じ規則）。引き継ぎ先のない目安は、期日と違って付け直しを求めず、そのまま使わなくなります。
- 完了・解決した項目と、誤りとして外した項目の目安は付けも外しもできません。戻すと、片付ける前の目安のまま戻ります。
- アプリから今と同じ目安を重ねて依頼したとき（別の端末や二度押し）は、望んだ状態になっているので記録を増やさずに受け付けます。CLIでは理由を示して断ります。

```sh
node packages/core/dist/cli.js --config "<設定ファイル>" item effort <project-id> <key> --set quick --confirm
node packages/core/dist/cli.js --config "<設定ファイル>" item effort <project-id> <key> --set none --confirm   # 外す
```

アプリの対応版では`operation: item-effort`の受付ファイル（`effort`に変更後の目安、`null`で外す）として依頼します。指定ごとに`90_system/item-efforts/EFF-*.json`を残し、項目ごとに最後の記録を有効とします。項目一覧（`90_system/now-items/`）の各項目にも、そのときの目安を`effort`として書きます。読めない記録はNOW・HOMEの生成を止めず、`doctor`で示します。

### 連絡待ち

人に頼んだことや、返事を待っていることは、自分では進められません。次の一手・未解決（本人が追加した行動とプロジェクト未定の行動を含む）に、本人が**連絡待ち**の印を付けられます（GTDの「連絡待ち」）。印には、待っている相手（任意・1行40文字まで）と頼んだ日（既定は付けた日）を残します。AIは印を付けません。印のないまま「回答待ち」と書かれた未解決は、これまでどおり未解決に並びます。

- 印を付けた項目は、HOMEの「次の一手」の一覧・期日の欄・見直す日まで休ませている件数から外し、「連絡待ち（N件）」の欄に頼んだ日の古い順で、相手と頼んでからの日数を付けてまとめます（期日・見直す日も行末に示します）。進行中のプロジェクトの項目と、プロジェクト未定の行動が対象です。プロジェクト未定の次の一手の欄では件数だけを示します。
- 連絡待ちに[見直す日](#期日と次に見直す日)を付けると、その日以降はHOMEの「次の一手」の先頭に「連絡待ちの確認」として出ます。返事が来ていれば印を外すか完了にし、まだなら催促して見直す日を付け直します。見直す日は、ほかの項目と同じ記録（`item-schedules`）です。
- 返事が来たら、印を外して元の欄へ戻すか、そのまま完了・解決にできます。完了・解決した項目の印は付けも外しもできず、未解決へ戻すと印も戻ります。
- NOWでは、項目を元の欄に置いたまま、行末に「連絡待ち 2026-11-10から」と示します。**相手の名前はNOWに載せません。** NOWは別AI向けの`context`・`bundle`の元になるためです。相手の名前は、項目一覧（`now-items`の`waiting.who`）・HOME・ふりかえり・人ごとの見返しとアプリにだけ示し、整理用のモデルへ渡す資料にも足しません。相手の名前はVaultに残るので、同期先の端末とバックアップにも入ります。気になる場合はイニシャルなどで書いてください。
- ふりかえり（REVIEW.md）には「連絡待ち」の欄を作り、件数と14日以上待っている件数、頼んだ日の古い順に5件を示します。
- 人ごとの見返しには、本文に名前が出てくる項目に加えて、連絡待ちの相手にその人の名前・呼び名を書いた項目も載せます（「連絡待ち 2026-11-10から」と付けます）。
- 作業要約が届いて根拠が変わっても、同じ欄・同じ本文の項目には印を引き継ぎます（期日と同じ規則）。引き継ぎ先のない印は、手間の目安と同じく付け直しを求めません。AIの行を「自分の行動にする」で引き取ると、元の行の印も行動の記録として写します。
- アプリから今と同じ印を重ねて依頼したとき（別の端末や二度押し）は、記録を増やさずに受け付けます。CLIでは理由を示して断ります。

```sh
node packages/core/dist/cli.js --config "<設定ファイル>" item wait <project-id> <key> --who "山田さん" --since 2026-11-10 --confirm
node packages/core/dist/cli.js --config "<設定ファイル>" item wait <project-id> <key> --confirm            # 相手なし・頼んだ日は今日
node packages/core/dist/cli.js --config "<設定ファイル>" item wait <project-id> <key> --clear --confirm    # 外す
```

アプリの対応版では`operation: item-wait`の受付ファイル（`waiting`に変更後の全体`{who?, since}`、`null`で外す）として依頼します。頼んだ日は今日まで（端末とのタイムゾーンの違いを見込み、翌日までは受け付けます）。指定ごとに`90_system/item-waits/WAIT-*.json`を残し、項目ごとに最後の記録を有効とします。項目一覧（`90_system/now-items/`）の各項目にも、そのときの印を`waiting`（`id`・`since`・`who`）として書きます。読めない記録はNOW・HOMEの生成を止めず、HOMEの「失敗と競合」と`doctor`で示します。プロジェクト未定の行動への依頼は、置き場`_unassigned`で送ります（`item_record_scopes`）。

### 期日をカレンダーに出す

設定で有効にすると、HOMEを作るたび（`cycle`・`dashboard`）に、進行中のプロジェクトの次の一手・未解決と、プロジェクト未定の本人が追加した行動に本人が付けた期日を、カレンダーに読み込める`90_system/calendar/contexthub.ics`（iCalendar）へ書き出します。既定は無効です。

```json
"calendar": { "enabled": true, "reviewDates": false, "titles": "item" }
```

- 期日は終日の予定になります。`reviewDates`を`true`にすると、次に見直す日も「[見直す日]」の予定にします。
- 予定の識別子（UID）は項目のキーから決めるため、日付を変えて読み込み直しても予定は増えずに置き換わります（日付を変えずに本文や`calendar.titles`だけが変わった場合、カレンダーのアプリによっては前の件名のまま残ることがあります。購読ではなく読み込みで使うときは、その予定を消してから読み込み直してください）。完了・解決・誤りとして外した項目、日付を外した項目、休止・完了したプロジェクトの項目は予定から消えます。
- カレンダーはGoogleやiCloudなどへ同期されることが多いため、件名と説明には[伏せ字](operations.md#秘密情報らしい文字列を伏せる)の規則を当てます。`titles`を`project`にすると、件名と説明に項目の本文を入れず、「[期日] プロジェクト名: 次の一手」の形にします。
- 内容が変わったときだけ書き、同期でほかの端末にも届きます。無効に戻すと、以前に書いたファイルを消します。
- ファイルをカレンダーアプリで開くと取り込めます。ローカルのファイルを購読として自動で更新し続けられるかはカレンダーアプリによるため、変更を反映するには読み込み直してください。アプリ（ContextHub Flutter）の対応版では、期日のある項目から1件ずつカレンダーへ入れることもできます。

## コミット履歴からの作業記録の下書き

既定では無効です。設定ファイルで本人が指定したローカルリポジトリだけを、Mac miniで読み取り専用で参照します。

```json
{
  "git": {
    "enabled": true,
    "repos": [{ "projectId": "context-hub", "path": "/Users/me/dev/context-hub", "name": "context-hub" }],
    "maxCommits": 30,
    "lookbackDays": 14
  }
}
```

`cycle`（または`git collect`）は、進行中のプロジェクトに設定したリポジトリごとに、まだ下書きにしていないコミットを`git log`で集め、下書きを1件作ります。対象は前回の下書きの最新コミットより後（`<sha>..HEAD`）です。下書きがない場合や、そのコミットが履歴から消えた場合は、プロジェクトの最終根拠以降を日時で読みます。日時で読むときは`lookbackDays`日より前には遡りません。マージコミットは除き、件名だけを使います。差分・作者・メールアドレスは読みません。1件の下書きには古い順に最大`maxCommits`件を、入力の文字数上限（`capture.maxInputChars`）に収まる分だけ入れ、残りは次の下書きに回します。

gitはシェルを介さず固定引数で実行します。ページャ・fsmonitor・署名検証は使わず、継承した`GIT_*`環境変数も渡しません。`path`には`~/`も使えます。同じリポジトリは重ねて設定できません。読み取れないリポジトリや、存在しないプロジェクトの設定があっても`cycle`は止めず、HOMEの「失敗と競合」に表示します。

下書きは入力ではありません。`90_system/git-drafts/GDR-*.json`に保存し、HOMEの「作業記録の下書き」に表示します。未確認の下書きが残っているリポジトリでは、確認されるまで次の下書きを作りません。休止・完了のプロジェクトは対象外です。

- アプリでは、下書きの本文を入力フォームに読み込み、本人が編集してメモまたは作業要約として保存します。保存した入力には`meta.git_draft`（下書きID）と`meta.git_draft_hash`（確認した下書きのハッシュ）が付きます。同じプロジェクトで、両方が一致する入力ができたときだけ、下書きを使用済みにします。
- 見送る場合は`operation: git-draft-dismiss`の受付ファイルで依頼します。見送った下書きのコミットは、以後の下書きに含めません。
- CLIでは本文をそのまま入力にするか、見送ります。

```sh
node packages/core/dist/cli.js --config "<設定ファイル>" git drafts
node packages/core/dist/cli.js --config "<設定ファイル>" git use <GDR-ID> --hash <sha256> --kind memo --confirm
node packages/core/dist/cli.js --config "<設定ファイル>" git dismiss <GDR-ID> --hash <sha256> --confirm
```
