# 運用・停止・バックアップ・復元

本体コードと配布ファイルの更新には[共通更新コマンド](deployment.md)を使えます。更新履歴・バックアップはVault外の運用先に保存し、`status`で適用版と未完了操作を確認します。

## 普段の確認

HOMEで受領、整理待ち、失敗、競合、停滞しているプロジェクトを確認します。[週次の統合](weekly-synthesis.md)を有効にしている場合は、先頭に「今週の気づき」を出します。HOMEは行動につながる欄から順に、「次の一手（進行中のプロジェクト）」「[プロジェクト未定の次の一手](work-records.md#プロジェクト未定の次の一手)」「プロジェクト一覧」「確認待ち」と並べ、受領と整理の状況、失敗と競合は末尾に置きます。「受領と整理状況」は、件数を1行で示したうえで、受付待ち・内容変更・整理待ち・整理失敗を全件、受領済み・整理済みは新しい5件ずつを並べ、それより古いものは件数だけを示します（全件はアプリの受付状況で確認できます）。数日あいたときは[REVIEW.md](project-lifecycle.md#ふりかえりreviewmd)で直近の変化を確認します。片付いた次の一手・未解決は[完了・解決](work-records.md)として報告し、コミット履歴から作った[作業記録の下書き](work-records.md#コミット履歴からの作業記録の下書き)はHOMEで確認します。NOWは生成時点と最終根拠の日時を持つビューです。同期100%と本人の表示確認、AI内容の正しさはそれぞれ別に確認します。

```sh
node packages/core/dist/cli.js --config "<設定ファイル>" doctor
node packages/core/dist/cli.js --config "<設定ファイル>" pending
node packages/core/dist/cli.js --config "<設定ファイル>" find "<検索語>"
node packages/core/dist/cli.js --config "<設定ファイル>" find --project "<project-id>" --kind memo,work-summary --since 2026-10-01
node packages/core/dist/cli.js --config "<設定ファイル>" context "<project-id>" --max-chars 6000
node packages/core/dist/cli.js --config "<設定ファイル>" bundle IN-... IDEA-... "<project-id>" --max-chars 12000
node packages/core/dist/cli.js --config "<設定ファイル>" digest
```

`doctor`は異常を`issues`に返し、1件でもあれば終了コード1で終わります。見つからない作業フォルダーの対応付け（外付けドライブを外したなど）は異常ではなく注意として`notices`に返し、終了コードに影響しません。

`find`は空白区切りの語をすべて含む記録を、一致数の多い順に最大50件返します。`--project`（帰属・関連するプロジェクト。AI推定の関連は「関連候補（AI推定、帰属未確定）」と表示）、`--kind`（`memo`・`work-summary`・`action`（本人が追加した行動）・`correction`・`idea`・`knowledge`・`now`・`reference`のカンマ区切り。`reference`は[参考資料](project-lifecycle.md#資料referencesmd)に分類されたメモ）、`--since`・`--until`（`YYYY-MM-DD`は日本時間の日付、またはタイムゾーン付き日時）で絞り込めます。絞り込み条件があれば検索語は省略でき、その場合は新しい順に並べます。`--sort newest`で新しい順、`--limit`（1〜200）と`--offset`で続きを読めます。期間と新しい順は、原文は発生日時、NOWは最終根拠の日時、アイデアは元のメモの発生日時、知識は採用日時で判断します。共通の知識はプロジェクトで絞り込んだ結果に含めず、[統合済み](project-lifecycle.md#プロジェクトの統合)のプロジェクトを指定すると統合先で絞り込み、分類を取り消したアイデアは`--kind idea`に含めません。

`context`は1つのプロジェクトのNOWと関連メモ最新10件を決まった形で出します。特定の記録だけを別のAIへ渡したいときは`bundle`を使います。`find`で表示されたID（原文の`IN-`、アイデアの`IDEA-`、知識の`KNW-`、NOWはプロジェクトID）を最大50件、渡したい順に並べます。原文は訂正があれば最新の訂正の本文と訂正の注意を出し、本人が指定したプロジェクトとAI推定の関連を分けて示します。NOWは自動領域だけを出し、NOWがまだないプロジェクトは「不明」とします。本文は```で囲み、本文中の見出しが別の記録や方針に見えないようにします。AIの整理結果（有効解釈）は未検証と示します。先頭には共通方針と、記録が属するプロジェクト（本人指定・NOW・プロジェクト知識の所属）の方針を付けます。AI推定の関連だけのプロジェクトの方針は付けません。上限（既定は`retrieve.contextMaxChars`）に収まらない記録は本文の途中で切らずに丸ごと省き、末尾にIDを示します。Mac・Androidアプリの「文脈かご」も同じ考え方で記録を束ねます。

## 似ているアイデアを束ねる

同じ思いつきを日を変えて何度もメモすると、`20_ideas/`に別々のアイデアが増えます。`cycle`（HOMEの生成）のたびに、アイデアの要約どうしの似ている度合いをAIを使わずに計算し（NFKCで正規化した文字bi-gramのDice係数。0.4以上を候補）、HOMEの「似ているアイデア」と`90_system/idea-index.json`（アプリが読む派生ファイル）に載せます。

```sh
node packages/core/dist/cli.js --config "<設定ファイル>" idea similar
node packages/core/dist/cli.js --config "<設定ファイル>" idea link "<IDEA-ID>" "<IDEA-ID>" --hash-a "<sha256>" --hash-b "<sha256>" --confirm
node packages/core/dist/cli.js --config "<設定ファイル>" idea separate "<IDEA-ID>" "<IDEA-ID>" --confirm
node packages/core/dist/cli.js --config "<設定ファイル>" idea groups
```

`idea link`は本人が「同じ話」と確かめた組を束ねます。ハッシュは`idea similar`で確認したIDEAファイルのもので、その後にアイデアが作り直されていれば束ねません。`idea separate`は別の話として候補から外し、束ねた組に使うと束から外します。判断は`90_system/idea-links/`に記録し、IDEAファイルと原文は書き換えません。束ねたアイデアは、`find`では一致した中で最も上位の1件にまとめ、ほかのアイデアへのリンクを添えます。HOMEでは元のメモが最も新しいアイデアを代表として先頭に出します。アプリからも同じ判断を依頼できます（受付操作`idea-link`）。

言い換えの多い文は似ていると判定されにくく、言い回しが似ているだけの別の話が候補になることもあります。候補は判断の材料で、自動では束ねません。

## 秘密情報らしい文字列を伏せる

メモや作業要約に紛れたAPIキー・トークン・パスワード・秘密鍵らしい文字列は、整理用のモデルへ渡す前と、`context`・`bundle`（別AI向けの資料）の出力、DiscordのOpenClawツール（`/ctx_find`・`/ctx_recent`・`/ctx_pending`・`/ctx_resume`）の返信で`[伏せ字:APIキー]`のように置き換えます。モデルの応答に同じ形の文字列が残っていた場合も伏せてから検証します。既定で有効です。原文（`00_inbox/`）は書き換えないため、同期先の端末とバックアップには元の値が残ります。HOMEの「秘密情報らしい文字列を含むメモ」（新しい10件。値は出しません）と`doctor`の`secrets`で該当するメモを確認し、本当に秘密の値なら発行元で無効化・再発行してください。

検出するのは、既知の形式（Anthropic・OpenAI・GitHub・GitLab・AWS・Google・Slack・StripeのキーやトークンとJWT、秘密鍵のブロック、`Bearer`の値、URLに埋め込んだパスワード）、`password=`・`DB_PASSWORD=`・`api_key:`・`パスワード：`のような代入の値（URLのクエリの`token=`・`sig=`も含む。半角の`,`・`;`で値が終わります）、`pass:`・`pass=`の値と「パスワードは hunter2…」「パスワードは「hunter2」」のように「は」で続けた値（どちらも英数字・記号で、数字か記号を含む6文字以上。`First pass: refactoring`のような文は伏せません）、英大文字・小文字・数字を含む32文字以上の高エントロピーな文字列です。16進のハッシュやコミットID、ULID、UUID、ContextHubの記録ID、URLのパスの一部は伏せません。重なって見つかった箇所は1つの伏せ字にまとめます。設定で規則を追加したり、無効にしたりできます。

```json
"privacy": {
  "redactSecrets": true,
  "patterns": [{ "label": "社員番号", "pattern": "EMP-\\d{6}" }]
}
```

`patterns`はJavaScriptの正規表現（`gu`フラグで評価）で、`label`は伏せ字に出す種類名です。決まった規則による検出のため、見逃しも誤検出もありえます。秘密の値をメモに書かない運用が前提で、これは見逃しを減らすための補助です。アプリでも同じ組み込み規則で、保存の前に知らせ、「選んで深掘り」でClaude APIへ送る内容を伏せます。設定の`patterns`（追加の規則）と`redactSecrets`は、Mac miniが`ctx init`・`cycle`（HOMEの生成）のときに`90_system/privacy/patterns.json`へ書き出し（内容が変わったときだけ）、同期されたVaultを通じてアプリへ渡ります。設定を変えた後は、次の`cycle`が終わって同期されるまでアプリには届きません。正規表現はJavaScript（本体）とDart（アプリ）で解釈が異なることがあるため、アプリで解釈できない規則があれば、アプリは取りこぼしを避けてVaultの内容をClaude APIへ送りません。追加規則は両方で同じに解釈される基本的な書き方（文字クラス・量指定・グループ程度）にしてください。追加規則は、アプリ（Dart）でも解釈できる書き方に限ります。インライン修飾子（`(?i:…)`・`(?-i:…)`など）や同じ名前の名前付きグループは、本体の設定検証で拒否し、どの規則（`privacy.patterns.<番号>.pattern`）が何故使えないかを示します（先読み・後読み・名前付きグループは使えます）。

原文や生成物を手動で書き換える前に、訂正履歴と競合を確認してください。生成物の競合は[生成版に戻す](#nowの更新が止まったとき生成物の競合)手順で片付け、退避ファイルを手で削除しないでください。同期による削除はほかの端末にも伝わるため、同期だけをバックアップとして扱いません。

## NOWの更新が止まったとき（生成物の競合）

NOW・HOME・REVIEWの生成領域を手で書き換えると、本体は手で書いた内容を上書きせず、新しい生成版を`90_system/conflicts/`へ退避します。そのNOWは手で書き換えた時点から更新されません。HOMEの「失敗と競合」に「NOWの更新が止まっています」と出たら、差分を確認して生成版に戻します。

```sh
node packages/core/dist/cli.js --config "<設定ファイル>" conflict list
node packages/core/dist/cli.js --config "<設定ファイル>" conflict resolve 10_projects/<project-id>/NOW.md --hash <sha256> --confirm
```

- `conflict list`は対象ごとに、最新の退避、止まった時点、確認用ハッシュ、手で変えた行を表示します。手で変えた行は、最後に書いたNOWの自動領域（`90_system/now-generated/`）と比べます。基準がない旧版のNOWは最新の退避と比べるため、生成側の変化も含まれることがあります。
- `resolve`はNOWで手で変えた行を、そのプロジェクトのメモ（`memo`）として先に保存します。保存しない場合は`--no-memo`を付けます。次に退避を`90_system/conflict-archive/`へ移し、最新の入力からNOWを作り直します（自動領域の外の手動領域は保持）。置き換える前の全文は`90_system/conflict-resolutions/CRS-*.json`に残ります。メモ・記録・退避・作り直しは1つのWriterロック内で行い、確認後にNOWが変わっていれば何も変えずに止めます。
- 手で変えた行は、最後に書いたNOWの生成版（`90_system/now-generated/<id>.json`）と比べて求めます。この基準がない旧版のNOWでは最新の退避と比べ、出典付きの行（生成側の更新と手で直した行を区別できない行）はメモに含めません。その場合も置き換えた全文は記録に残ります。
- 途中で止まった場合は、同じ受付IDの再送で記録に結び付いた退避の片付けと作り直しだけを続けます。記録後に手で書き換えたNOWや、新しく退避された競合はそのまま残します。
- HOME.md・REVIEW.mdは派生の一覧なので、メモは作らずに作り直します。それ以外（アイデア・候補など）の競合は対象外です。
- 確認後に対象が変わっていれば受け付けません。アプリからは`operation: conflict-resolve`（`target`、`target_hash`、`confirmed: true`）の受付ファイルで依頼します。
- 同じ対象の退避は再生成のたびに増やさず、最新の1件を書き直します。

本人のメモはNOWの自動領域の外（手動領域）に書けば、再生成しても保持されます。

## 停止と再開

導入時に登録したジョブID・サービス・プロファイルを記録します。定期ジョブの状態は、導入版の`openclaw automations show <job-id>`で確認し、停止は同じIDのdisableを使います。取得や状態確認のためにモデルを実行する必要はありません。

SyncthingがKeepAliveで管理されている場合、GUIの終了だけでは再起動されることがあります。登録元のサービス管理から停止し、同じプロファイルの親子プロセスがすべて終了してから再開します。起動済みの同じプロファイルを別の方法でも起動しません。

CLI（`ctx`）はCtrl+C・SIGTERM・SIGHUPで終了するとき、自分が保持しているロックを解放してから終了します（途中で止まった操作は次回の実行で記録から回復します）。強制終了（SIGKILL）や電源断ではロックが残ります。ロック残骸がある場合は、全Writer停止と所有PIDの終了を確認してからdoctorのunlock手順を検討します。doctorはWriterロックと整理用ロックを区別して報告し、`--unlock`は両方の死亡PIDの残骸を回収します。設定の`organize.lockStaleSec`は使われていないため、設定例から削除しました。旧設定に残っていても読み込めます。稼働中のロックを手動削除しません。失敗した整理の再試行は対象と送信情報を確認して`--retry-failed`を明示し、成功済み入力を繰り返しモデルへ送らないでください。

## バックアップ

`scripts/vault-backup.sh`はmacOS向けの例です（Linuxでも動きます）。tarを使い、既定30日を超えた所定名のアーカイブを削除します。保存先と保持日数を確認し、必要なら別媒体にも複製してください。このスクリプト自身はWriterや同期を停止せず、Writerロックも取りません。各ファイルは一時ファイルからの置き換えで書くため完成したものだけが入りますが、複数のファイルにまたがる操作（受付・承認・統合など）の途中の状態が入ることがあります。これらの操作は記録を先に書いて停止後に回復する設計のため、復元後の`cycle`で続きが行われます。

整合した復元点を作るときは、まずWriterと同期を止め、書き込みがないことを確認します。実行例のパスを自分のものへ置換してください。

```sh
CTX_VAULT="<Vaultの絶対パス>" CTX_BACKUP_DIR="<Vault外のバックアップ先>" CTX_BACKUP_KEEP_DAYS=30 sh scripts/vault-backup.sh
```

launchd例を使う場合は、EnvironmentVariablesの`__VAULT_PATH__`と`__BACKUP_DIR__`へ、上の手動実行と同じ値を指定し、保持日数も確認してから登録します。バックアップには個人情報が含まれるため、ソースrepoや同期Vaultへ保存しません。

## バックアップを暗号化する（任意）

暗号化しないtar.gzには、メモの原文などの個人情報がそのまま入ります。クラウドストレージや持ち出す外付けドライブなど、Mac miniの外にも置きたいときは、[age](https://github.com/FiloSottile/age)の公開鍵で暗号化します。暗号化は任意で、次の`CTX_BACKUP_AGE_RECIPIENTS`を指定しなければ、今までどおり暗号化しない`vault-YYYYMMDD-HHMMSS.tar.gz`を作ります。

1. ageを入れ（例: `brew install age`）、鍵の組を作ります。秘密鍵（`AGE-SECRET-KEY-1…`）と公開鍵（`age1…`）が分かれます。

   ```sh
   age-keygen -o "<秘密鍵のファイル>"
   age-keygen -y "<秘密鍵のファイル>" > "<公開鍵のファイル>"
   chmod 600 "<秘密鍵のファイル>"
   ```

2. 秘密鍵は、Vault・同期フォルダー・バックアップ先のどれにも入らない場所に置きます。同じ秘密鍵を、パスワードマネージャーや紙など、Mac miniとは別の場所にも必ず保管してください。秘密鍵をなくすと、暗号化したバックアップからは誰も復元できません。Mac miniが壊れたときに復元するのも、この別の場所の秘密鍵です。
3. バックアップのスクリプトに公開鍵のファイルを渡します。

   ```sh
   CTX_VAULT="<Vaultの絶対パス>" CTX_BACKUP_DIR="<Vault外のバックアップ先>" CTX_BACKUP_AGE_RECIPIENTS="<公開鍵のファイル>" sh scripts/vault-backup.sh
   ```

   `vault-YYYYMMDD-HHMMSS.tar.gz.age`ができます。スクリプトは、平文のtar.gzを一時フォルダー（`CTX_BACKUP_WORK_DIR`、既定はOSの一時フォルダー）で作って読めることを確かめ、暗号化したものだけを保存先へ置き、平文は消します。途中で止められた（Ctrl-C・launchdの停止など）ときも平文を消してから終わり、電源断などで残った2日以上前の平文（`ctx-backup-`で始まるフォルダー）は次の実行で消します。一時フォルダーがVaultや保存先の中にあるとき、受取人のファイルに秘密鍵が入っているとき、公開鍵がないとき、ageが見つからないときは、何も作らずに止めます。launchdはPATHが短いため、EnvironmentVariablesに`CTX_BACKUP_AGE_RECIPIENTS`と、`CTX_BACKUP_AGE`（ageの絶対パス。例: `/opt/homebrew/bin/age`）を追加します。保持日数は、暗号化したものとしないものの両方に同じように当てます。

4. 暗号化したバックアップを`backup verify`で確かめるには、設定に秘密鍵のファイルを書きます。設定がなければ、暗号化したアーカイブは「確かめられない」として、確認結果を記録せずに止まります（終了コードは0以外です）。

   ```json
   "backup": { "dir": "<Vault外のバックアップ先>", "verifyMaxAgeDays": 7, "ageIdentity": "<秘密鍵のファイル>", "ageCommand": "/opt/homebrew/bin/age" }
   ```

   `ageIdentity`はVaultの中にもバックアップ先の中にも設定できません。`ageCommand`は省略すると`age`です。確認ではageで復号した出力をそのまま展開し、平文のアーカイブをファイルとしては残しません。鍵が違う、壊れている、途中で切れているアーカイブは「暗号化したアーカイブを復号できません」として、復元できない確認として記録します。復号できたときの確認の内容は、暗号化しないアーカイブと同じです。HOMEの1行は「最後に確かめた復元点: 2026-11-01 03:30の暗号化したバックアップ（…）」になり、確認記録に`encrypted: true`を残します。秘密鍵の中身と場所は記録しません。パスフレーズで守った秘密鍵は無人の確認では入力できないため、`ageIdentity`には指定できません（確認を始める前に止めます）。

秘密鍵をMac miniに置くと、Mac miniを使える人は暗号化したバックアップも読めます。Mac miniにはもともと平文のVaultがあるため、暗号化で守るのは、Mac miniの外に置いたバックアップです。`backup verify`をMac miniで動かさない場合は、`ageIdentity`を書かず、秘密鍵のある別のMacでバックアップを写してから確かめることもできます。

別の場所へ写すときは、暗号化した`.tar.gz.age`だけを写します（例: rcloneやクラウドストレージの同期フォルダーへのコピー）。暗号化しないtar.gzをMac miniの外へ置かないでください。暗号化しても、ファイルの大きさとバックアップの日時は隠れません。

## バックアップから復元できるかを確かめる

バックアップは、展開して中身を確かめるまで復元できるか分かりません。`backup verify`は、アーカイブをVaultの外の一時フォルダーへ展開して確かめ、結果を`90_system/backup-checks/BKC-*.json`へ記録します。元のVaultは読むだけで、アーカイブも書き換えません。モデルは呼びません。

```sh
node packages/core/dist/cli.js --config "<設定ファイル>" backup verify
node packages/core/dist/cli.js --config "<設定ファイル>" backup verify --archive "<確かめるアーカイブ>"
node packages/core/dist/cli.js --config "<設定ファイル>" backup status
```

`--archive`を省くと、設定の`backup.dir`にある`vault-YYYYMMDD-HHMMSS.tar.gz`と、暗号化した`vault-YYYYMMDD-HHMMSS.tar.gz.age`のうち、いちばん新しいものを確かめます。暗号化したものの確かめ方は[バックアップを暗号化する](#バックアップを暗号化する任意)を参照してください。設定には次を追加します（どちらも任意）。

```json
"backup": { "dir": "<Vault外のバックアップ先>", "verifyMaxAgeDays": 7 }
```

確かめる内容は次のとおりです。

- アーカイブを最後まで読めること。通常ファイルとディレクトリ以外（リンク、特殊ファイル）、絶対パス、親ディレクトリへ抜けるパス、重複したパス、ファイルと同じ名前のフォルダーの中身は展開せずに問題として記録します。`._`で始まるAppleDoubleは展開しません。
- 展開した中身がVaultとして読めること（`90_system`・`00_inbox`、入力の原文、receipt、プロジェクトの定義）。
- 展開した原文が、現在のVaultの同じ入力と同じ内容であること。バックアップの作成より10分以上前に受け取った入力が、バックアップに入っていること。バックアップの作成時刻はファイルの更新時刻で判断します。別の媒体から写し直すなどして、更新時刻が所定の名前（`vault-YYYYMMDD-HHMMSS.tar.gz`）の日時より1日以上新しいときは、名前の日時（設定のタイムゾーン）を使います。
- 展開したコピーに対する`doctor`の結果（参考情報として記録します。復元できるかの判定には使いません）。

結果は次の場所へ出ます。

- HOMEの上部に「最後に確かめた復元点: 2026-11-01 03:30のバックアップ（3日前 / 今日復元できることを確認）」を1行で示します。確かめた復元点は、復元できた確認のうち、いちばん新しいバックアップです。古いアーカイブを後から確かめても、復元点は古くなりません。
- 最後に確かめたバックアップが復元できなかったとき、確かめた復元点が`verifyMaxAgeDays`日より古いとき、`backup.dir`を設定したのにまだ一度も確かめていないときは、HOMEの「失敗と競合」に示します。`backup.dir`を設定せず、一度も確かめていない間は何も示しません。
- `doctor`は`backup`として復元点と注意を返します。古い・未確認は`issues`には数えません（壊れた確認記録だけを数えます）。
- `backup verify`は、復元できないと判定したとき終了コード1で終わります。

確認記録にはアーカイブのファイル名だけを残し、保存先のパスは残しません。確認したときの`verifyMaxAgeDays`も記録し、設定を読めないアプリが同じ目安で復元点の古さを知らせます。記録は新しい30件と、最後に復元できた1件を残します。展開先は確認後に削除します。中身を自分で見たいときは`--keep`を付け、見終わったら自分で削除してください（`ctx-backup-restored-`で始まるフォルダーに残します）。確認が途中で止まって残った展開先（`ctx-backup-verify-`で始まる、1日以上前のフォルダー）は、次の確認のときに片付けます。展開先はOSの一時フォルダーに作ります。同期フォルダーの外の別の場所にしたいときは`--work-dir`で親フォルダーを指定します。展開にはVaultと同じくらいの空き容量が必要です。展開する大きさは、現在のVaultの4倍（小さいVaultでも256MiB、最大64GiB）と、展開先の空き容量から256MiBを残した分までにし、それを超えるアーカイブは復元できないと記録します。空き容量がVaultの大きさに満たないときは展開せずに止めます。

定期的に確かめるには、`examples/launchd/com.context-hub.backup-verify.plist`（週1回の例）を使います。`__NODE_BIN__`、`__REPO_PATH__`、`__CONFIG_PATH__`、`__HOME__`を実際の絶対パスへ置換してから登録してください。この確認は「アーカイブを展開でき、原文が現在と一致する」ことまでを見ます。別の端末で実際に運用へ切り替える手順は、次の復元テストで確かめます。

## 復元テスト

1. 信頼できるアーカイブのハッシュと一覧を確認し、絶対パス、親ディレクトリへ抜けるパス、リンク、特殊ファイルがないことを確認する。
2. 元Vaultを上書きせず、同期対象外の新しい空フォルダーへ展開する。
3. 別の設定・state・ログを用意し、provider=mockと復元先の絶対パスを明示する。
4. 展開後の正本ファイルのハッシュ、doctor、検索、プロジェクト再開、訂正・承認履歴を確認する。
5. 切り替えの対象と影響を確認してから、Writerと同期を再開する。

macOSのtarにはAppleDouble付加メタデータが含まれる場合があります。別の展開方法で`._`ファイルが現れたときは、原文やJSON記録と混同せず、内容を確認してVault外へ保全します。doctorのエラーを消すために正本を削除・改変しないでください。

古い実装へ戻す場合、新しい形式のreceiptや訂正記録をそのまま渡せるとは限りません。読む全ファイルの形式と内容を旧版で確認するか、別Vaultへ旧スナップショットを復元して検証します。

## 情報と費用

Discord入口の本文はDiscordを経由し、実AI整理の対象原文・出典・プロジェクト定義は設定済みのモデルで処理されます。[週次の統合](weekly-synthesis.md)を有効にした場合は、上限までのメモの本文または要約と、登録済みのプロジェクトの名前を、間隔ごとに同じモデルへ渡します（既定では無効）。Codex・Claude Codeが直接読んだ本文も、それぞれ選択したモデルで扱われます。必要な範囲だけを参照し、秘密情報や全文履歴を集めません。整理用のモデル、`context`・`bundle`、OpenClawへ渡す方針とDiscordのツールの返信へは、秘密情報らしい文字列を[伏せ字](#秘密情報らしい文字列を伏せる)にして渡します（Codex・Claude CodeがVaultを直接読む場合と、本人の端末で使うCLIの`find`・`recent`・`pending`・`resume`は伏せません）。

CLIのタイムアウトがGateway側の推論停止や課金停止まで保証するものではありません。厳密な費用上限はモデル提供側の設定と契約でも確認してください。整理のプロンプト（伏せ字にした本文・訂正履歴・有効方針）と、週次の統合のプロンプト（伏せ字にしたメモの本文・要約）は、OpenClawの`infer model run --prompt`の引数として渡します（OpenClaw側に標準入力から渡す方法がないための制約です）。実行中は、同じMacで`ps`などのプロセス一覧を読める利用者・プログラムから本文が見えることがあります。Mac miniを他の利用者と共有しない、ログインできる利用者を本人に限る、という前提で運用してください。ローカルのプロセス引数や同期フォルダーを読める利用者・プログラムは信頼する運用を前提とします。
